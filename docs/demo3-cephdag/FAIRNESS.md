# Is the disaggregated baseline fair? (pilots of 2026-11-13, analysis only)

Read-only analysis of the three pilot campaigns in PILOTS.md (cephdag demo3 `e81d66c`, whole-array
kernel, tbf 400 Mbit). Since then demo3 gained a chunked kernel (`9ca8ce7`) that removes the
memory-bus contention and cuts per-task compute about 12× at 8 concurrent tasks. That makes the
low-intensity cases even more I/O-bound, so the serial-worker finding below applies to more of the
next sweep, and the compute-contention points become moot. No runs, no lab or code changes. Every number below comes from the per-task
records in the run JSON files and is regenerated by `demo3/fairness_analysis.py` (method at the end).
"Measured" means read from those records; "estimated" means computed from them under a stated model.

## Findings

**Bounds.** cs runs at its bound; disagg does not. The best cs policy is within 0.97–1.02 of the
per-node bound (local I/O at calibrated rates plus measured compute) at P1 i1, P1 i128 and DROID.
Disagg runs at 1.59–1.67 of its link bound at P1 i1 (18.1 s against 11.4 s), 1.65–1.71 at P1 i128
(there the bound is the busiest worker's compute), and 2.65–2.99 on DROID (158.9 s against 60.0 s,
n5's 2.83 GB). The exception is P3 skew i1, where disagg is at 1.01 of its bound: n0's link is busy
99.5 % of the run (97 % of it shared by two or more readers), so nothing else matters there. The
two bounds are not the same kind: the cs bound is a per-node sum, the disagg bound assumes the
storage links never idle.

**Where disagg's extra time goes.** Each worker runs one task at a time: it reads all inputs, then
computes, then writes, then publishes (`worker.py` `execute_payload`; `DurableWorker._start` refuses a
second job; `model.Simulation.free_workers` offers only idle workers to the policies). The next task
is submitted only after the coordinator has seen the completion. So a disagg worker's receive link
idles while it writes, and its send link idles while it reads.

- P1 i1, disagg heft, per worker (sums to the wall): 11.4 s receiving at line rate, +1.3 s per-read
  cost (each 64 MiB read runs at 42.7 MB/s against 47.1, no read ever shared a link), +2.9 s writing
  at line rate after the reads, +1.2 s from writes that shared a storage node's receive link (22 of 64
  writes, at 23 MB/s against 43 alone; hash placement), +0.2 s compute, +0.9 s dispatch, +0.4 s idle
  at the end. The storage-node send links were active only 66–70 % of the run.
- DROID, disagg heft, per worker on average: 52 s receiving at line rate, +34 s because 40 % of bulk
  reads shared a storage node's link (23 MB/s against 43), +29 s writing at line rate, +8 s write
  slowdown, +23 s compute, +5 s dispatch, +7.5 s idle at the end. The storage tier's total egress
  never exceeded 64 % in any 1 s bin and was 17–48 % in 10 s windows. The single-slot serial floor
  (each worker's bytes at line rate plus its compute) is 104 s, against the 60 s link bound.
- fifo-hash on DROID is worse (179.5 s) because it sends the two consumers of each frames object to
  two workers at once: 103 of 118 frames objects were read twice concurrently from the same OSD, at
  22.6 MB/s each against 39.0 when apart. HEFT staggers them (0 of 118).

**Control plane.** The coordinator's loop is 2.5–3× slower in disagg: decision interval p50 38–49 ms
against 13–24 ms in cs (P1 i1 and DROID); per-task slack (submit plus completion detection) p50 29–66 ms against
16–23 ms; dispatch gap p90 up to 0.25 s (P1 fifo-hash) against ≤ 0.02 s for cs heft and data-local
(DROID gaps also include waits for a ready task).
The loop polls every worker, then dispatches one task, so when workers finish together the k-th waits
k loop rounds. The likely cause is that the coordinator runs in n0, whose NIC carries 1/8 of the
payload in disagg (and none under cs heft): its 5 ms `/state` polls (about 2.4 MB/s of control
traffic in LAB-VALIDATION finding 5) queue behind payload in n0's tbf. Compute-only workers also
journal every job to pool node0 (`worker.py`: `journal_pool=... or cluster.metadata_pool`). This is an inference: the RADOS completion-record writes to node0 are only slightly slower
(p50 9–11 ms against 7–10 ms), and in skew, where n0's link is saturated, slack and decision
interval rise to 92 and 125 ms. It costs disagg about 3–6 % of the wall at P1 i1 and about 2 % on
DROID.

**Verdict.** Yes: one slot per worker, strictly read → compute → write → publish, no prefetch,
in both modes. That is not how a real disaggregated system runs (executors with several slots,
prefetching readers, write-behind). It handicaps disagg most where its time is network I/O spread
over many links (DROID, low-to-mid intensity), and it also handicaps cs, whose local reads, compute
and writes are serial too. Re-timing every run as a two-stage pipeline (read the next task's inputs
while the current one computes and writes; same assignment, order and stage durations; never below
the link bound) gives these estimates:

| case | speedup now | read-ahead in disagg only | read-ahead in both | disagg at its link floor, cs with read-ahead |
|---|---|---|---|---|
| P1 i1 | 6.47 | 4.85 | 7.45–8.52 | 7.17 |
| P1 i128 | 1.07 | 0.75 | 0.79 (1.12 if disagg's compute slows to cs's per-task time) | 0.65 |
| DROID | 4.07 | 2.45 | 3.18–3.26 | 2.04 |
| P3 skew i1 | 5.25 | 5.20 | 6.51–11.88 | 11.88 |

- **P1 i1 (6.5×) survives.** With read-ahead in both modes it rises, because cs's own serial
  compute and writes hide behind its reads; it falls to 4.9× only if cs gets no overlap at all.
- **DROID (4.1×) is inflated by the serial worker.** A fair figure with overlap in both modes is
  about 3.2×, and about 2× if the disagg baseline reached its link bound.
- **The crossover moves left.** With overlap the curve reaches 1× near i64 (0.99) rather than i150;
  at i128 the estimate is 0.79–1.12, depending on whether disagg's compute slows once all its
  workers compute at once (it is 1.5× faster per task now, see below).
- **Skew (5.25×) is conservative.** Disagg is pinned at n0's link, and cs greedy-wait would gain from
  overlap.

**Other things that favour one mode.**

- *Favours cs, and the largest effect on DROID:* every stage's output is persisted in the storage
  tier. Of DROID's 30.3 GB moved in disagg, 24.1 GB is the frames intermediate (8.0 GB written, 16.1 GB
  read back by its two consumers); source plus final outputs are 6.2 GB, with the busiest storage NIC
  at 0.52 GB (11 s). Measured compute is 52 CPU-s per source GB (186.6 s for 3.61 GB), so one
  worker consumes about 20 MB/s of source, under the 47 MB/s link. Suppose an engine fused each
  partition's four tasks and kept the frames in memory, as Spark would. A disagg worker would then
  move 0.45 GB of source (9.6 s) and 0.32 GB of outputs (6.8 s) and compute for 23 s: about
  30–40 s with or without overlap. cs would lose its local frames I/O and finish in about 28–32 s.
  So DROID itself gives about 1.0–1.4× (estimated, not measured). The 4.1× holds for DAG
  pipelines that persist intermediates in shared storage, which is what cephdag models. It does not
  hold for DROID processing in general.
- *Favours cs:* the coordinator in n0 and node0 journals (above, 2–6 %); hash output placement
  collisions on writes (realistic for CRUSH, single replica).
- *Favours disagg:* lower memory-bus contention. Its workers spend most of their time reading, so
  fewer compute at once, and per-task compute is 1.51× (i128) to 1.58× (i64) faster than in cs. This
  advantage would disappear with overlap, and the chunked kernel removes it. Also, every input is SHA-256-hashed twice
  (`RadosStore.read`, then `execute_payload`), an equal absolute cost that is a larger share of cs's
  short local reads (P1 i1 cs reads: 64 MiB at 443 MB/s median including hashing). The split is not
  measured.
- *Neutral:* only cs nodes are warmed before a run (`run.py warm`), but disagg reads are
  network-bound, far below OSD read rates. The final-output verification read is outside the timer
  in both modes. Poll traffic passes through n0's NIC in both modes; it only costs disagg through
  queueing behind payload (above). Storage containers have 3 CPUs (OSD 1 + worker 2) and compute-only
  containers 2 (`infra/labs/cephdag8.json`); the kernels are single-threaded, so this does not
  matter as far as I can tell.
- *Bound caveat:* the v3 calibrated local read rates (256–324 MB/s) are below what the pilots' read
  stages achieved, so the cs bound is loose where n0 does most of the work (skew cs greedy-wait wall
  is 0.87 of it).

## Recommendations, ranked

Change before the full runs only what can be measured quickly. State the rest as caveats.

1. **Measure disagg with I/O overlap on DROID before presenting 4.1×.** This is the only harness
   artefact that moves a headline by more than about 10 %. The cheapest measured check needs no
   worker or policy code: start a second worker process in each compute container on another port
   and run disagg fifo-hash with 16 slots on 8 NICs. It needs a 24-node cluster file and models file
   (copy the compute-node entries) and Aakash's yes, because it starts processes in the lab. Run the
   DROID wave-0 pair plus P1 i1 and i128.
   - Expected (estimated): disagg DROID 159 → about 96–110 s; P1 i1 18.1 → about 13.6–14.3 s;
     i128 about 27–38 s. The read-ahead model gives the low ends. Two slots also share each
     worker's NIC and add storage-link sharing, hence the high ends.
   - Speedups against unchanged cs: DROID about 2.5×, P1 i1 about 4.9×, i128 about 0.75–1.07×. This
     is conservative for cs. The symmetric fix (read-ahead in the worker, in both modes) changes
     the worker, coordinator and policy contracts, plus a recalibration. It does not fit before
     Monday.
   - If neither is approved, present DROID as "4.1× measured with single-slot workers in both
     modes; about 3.2× estimated with I/O overlap in both, about 2× if disagg reached its link
     bound".
2. **State what DROID's speedup depends on.** It holds because intermediates are persisted in
   shared storage: 30.3 GB moved, against 6.2 GB of source and final outputs. A fused pipeline would
   be compute-bound in both modes, at about 1.0–1.4× (estimated). A fused-DROID pair would settle it,
   but it needs a new function and a worker restart, so it is a candidate for after Monday.
3. **Optional, otherwise a caveat: take the coordinator off a payload-carrying NIC.** Run it
   where its traffic is not queued behind data, the same in both modes, and spread compute-only
   workers' journals across pools instead of node0. Expected: disagg 3–6 % faster at low intensity
   (P1 i1 speedup 6.5 → about 6.1–6.3), about 2 % on DROID, no change to cs.
4. **Caveat only: dispatch one task per poll round.** Dispatching to every free worker per round
   would recover at most the dispatch gaps: 0.67 s per worker of 19.1 s (3.5 %) for disagg
   fifo-hash at i1, 0.19 s (1 %) for disagg heft, and about 0 elsewhere.
5. **Caveats for the demo slides.**
   - All workers are single-slot and serial in both modes; give the overlap band above.
   - With overlap, the 1× crossover is near i64–i128, on top of the memory-bus surprise in
     PILOTS.md.
   - Disagg's per-task compute benefits from lower memory-bus contention at high intensity.
   - Hash placement makes about a third of P1's writes share a storage link. This is realistic.
   - Each number is one repeat.

## Method

- **Data.** The run JSONs and `rows.jsonl` of `aakashpc:/mnt/mass/cephdag/campaigns/pilot-{sweep,droid,skew}/`
  (59 runs), copied with `tar` over ssh to the scratch directory
  `/home/aakash/.hermes/cache/scratch/fairness/raw/` (pruned after 24 h; re-copy to reproduce).
  Smoke runs (`/mnt/mass/cephdag/smoke/`) were copied but not used: they are 2 GiB versions of the same
  cases.
- **Timeline.** For each task the coordinator records `submitted` and `actual_finish` (coordinator
  clock, seconds from run start) and the worker's `result.seconds` and per-stage durations. Stages run
  strictly in sequence in `execute_payload`, so they are laid end to end from `submitted + slack/2`,
  where slack = `actual_finish − submitted − result.seconds` (p50 15–66 ms). Placement error is at
  most slack/2, well under the 1 s bins. `publish` is `result.seconds` minus the stage sum: the
  `complete.json` write to the journal pool (own pool in cs, node0 in disagg).
- **Links.** Input locations are rebuilt from the graph rules: synthetic shard i on
  `placement[i % len]` (sweep 0..7; skew seven 0s then 1..7); DROID partition j of shard s on node
  `(s + j) % 8`, with 21/34/32/31 partitions for shards 2–5 (driver.log), and frames/state on the
  pools recorded in the decode task's outputs. The rebuilt per-node payload bytes match
  `rows.jsonl` `network_payload_bytes.per_node` exactly for every run; the script checks this. Each
  remote read or write is one flow at a uniform rate over its stage.
- **Bounds.** Link: busiest node-direction bytes / 47.0875 MB/s (verified tbf goodput). Node (cs):
  local bytes at the run's calibrated `read_bps`/`write_bps` plus measured compute-stage seconds.
  Compute (disagg): the busiest worker's measured compute-stage seconds.
- **Read-ahead estimate.** Per worker, same tasks in the same order: reads back to back, and each
  task's compute + write + publish starts when its reads are done and the previous task's are done
  (`readahead()` in the script). The worker starts at its first measured submit. The result is never
  below the link bound. The model ignores the change in link sharing that overlap would cause, which
  is why the link floor is listed separately.
- **Not done.** No new runs, no packet-level measurement of the tbf queue at n0 (the control-plane
  cause is inferred), one repeat per point.
