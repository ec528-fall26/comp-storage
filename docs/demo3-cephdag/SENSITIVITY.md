## A. disagg2: two workers per compute-only container

Implemented as a third lab mode rather than a `--slots` option: the mode name has to reach
`check`, `verify`, the campaign spec and the result rows anyway, and the per-node worker
start code needed the same change either way.

**Lab changes it makes (needs Aakash's yes):** `python3 infra/lab.py --lab infra/labs/cephdag8.json mode disagg2`

- stops the storage-node workers (n0–n7) and starts the compute containers if they are
  stopped, exactly as `mode disagg` does;
- runs two `python3 -m cephdag.worker` processes in each of cephdag8-c0..c7: `--node 8+j`
  on 172.30.(152+j).10:8080 and `--node 16+j` on 172.30.(152+j).10:8081, both
  `--cluster cephdag/clusters/cephdag8-disagg2.json`, both appending to
  /var/lib/ceph/worker.log;
- if a container already runs other workers (for example disagg's single worker, whose
  `--cluster` differs), it stops them first (`stop_worker`, as now). It does not restart
  containers. Running it twice is a no-op ("its 2 workers are already running");
- it waits until all 16 workers answer /state, the same readiness check as the other modes.

**CPU quota: unchanged.** No `docker update`. Each compute container keeps 2 CPUs and 3072
MiB (infra/labs/cephdag8.json). A single worker peaked at 1.03 of its container's 2 CPUs:
cgroup sampling of the running chain at 0.5 s intervals, synthetic sweep. The kernels are
single-threaded (FFV1 is pinned to `thread_count = 1`). So two workers per container are a
pure overlap test without raising the quota. Memory: two tasks of at most 512 MiB plus about
130 MB of process baseline each fit in 3072 MiB.

**Coordinator view:** 8 storage-only nodes plus 16 compute-only nodes. Use only fifo-hash
there: the network model would give each second worker a NIC of its own. The models are
the disagg models with each compute entry repeated (`experiments.derive_models --slots 2`),
not recalibrated. Rows are labelled `mode: "disagg2"`. Both `network_tx_bytes` and
`network_interface_bytes` count each container's eth0 once, from its first worker; without
fbd33e8, disagg2 would have double-counted it.

**Tests.**
- In-process, 2 storage + 2×2 compute: fifo-hash outputs equal cs; all four workers run
  tasks at the same time (a barrier of 4); interface bytes are counted per host.
- lab.py on the fake host: disagg→disagg2→disagg2→disagg→disagg gives 2 or 1 workers per
  compute container, no container start or stop, and the right cluster file; repeats are
  no-ops.
- The disagg2 worker command lines are generated by the real lab code.

## B. droid_fused@1

`cephdag/droid.py` now builds all five functions from the same array-level helpers. The
fused function runs decode_resize, then encode_video, frame_stats and state_parquet, on one
partition in one task. It stores only the video, statistics and Parquet; frames and state
stay in memory.

**Byte equality (verified).** Scratch script
`~/.hermes/cache/scratch/sens/compare_refactor.py` checked every partition, comparing
2b22dd6's droid.py (the deployed one) with the new one:

- the new unfused frames, state, video, stats and Parquet have the same sha256 as 2b22dd6's;
- the fused outputs have the same sha256 as the unfused finals;
- this held on droid-mini (1 partition) and on real shard 217 (15 partitions).

In the test suite:

- `test_the_fused_function_returns_the_unfused_pipelines_outputs_byte_for_byte` checks the
  functions;
- an end-to-end test on two droid-mini partitions finds one `final_outputs_sha256` across
  unfused greedy, fused fifo-hash, fused heft and fused data-local. The fused run stores
  only the final types and writes under a third of the unfused bytes.

The campaign stops if a wave's variants disagree on that digest.

**Verification.** The checks are unchanged: video decoded back, statistics recomputed,
Parquet round trip, frames re-derived from the source JPEGs. For a fused partition the
frames and state are derived again from the source, so every frame is checked against the
JPEGs rather than a sample. A tampered fused video is rejected (test).

**Memory (measured).** Fresh process per task, at 128 px, on shard 217's largest partition
(45.7 MB, 590 steps). Task bytes = input plus RSS growth:

| task | task bytes |
|---|---|
| decode_resize | 308 MB |
| droid_fused | 217 MB |

The fused task is lower because it never packs the frames into an object.
`droid.fits_fused` reserves the decode task plus the frames and refuses a partition over 512 MiB:

- the partitions the cap allows fit unless their frames are under 1.33× the source
  (DROID's are 2.17×);
- every partition of shard 217 fits (test);
- the fused graph builder raises an error on a partition that does not fit.

Raw numbers: `~/.hermes/cache/scratch/sens/mem/peaks.jsonl`.

**Cost model.** `droid_workload.fused_cost` takes the four functions' calibrated
predictions, evaluated at the bytes each unfused task reads and writes per source byte
(frames 2.16× the source). It is not the plain sum of the coefficients, which charges
state_parquet's per-state-byte cost on every source byte and comes out more than 3× too
high (test). On the real cephdag8 models it gives **49.8 s per source GB** in both modes,
against 50.4 CPU-s/GB measured in LAB-VALIDATION.md. Output sizes are the unfused graph's
estimates of video, statistics and Parquet (test).

## C. Progress on stdout

The cause of the silence: the deployed driver printed only step starts, with a bare `print`.
That output is block-buffered when stdout is a file, which is why the chain's output.log
still holds only the `git log` line. driver.log gets only the lab commands' output.

Now each step prints `YYYY-MM-DD HH:MM:SS TZ <step>: attempt N started`, then
`completed in S s` or `failed: <reason>`. The campaign's start and end lines are printed the
same way, and every line is flushed. Tested.
